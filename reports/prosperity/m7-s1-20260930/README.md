## 过程

1. 第一次运行：92.9%（6140/6610），未达标，报错 1 行（WBD）。按计划停下来报 Boss，没有改阈值，也没有改代码去凑数。
2. 诊断发现三处问题，Boss 逐项批准后处理：
   - **一家公司只看一个代码**：GOOGL 与 GOOG 每期同榜，BRK.A 与 BRK.B 同榜。改为复用 `security_master.share_class_of`，也就是我们池子剔除次要股类的同一条规则 → 93.9%。

   - **可用日期兜底**：FMP 把一些季度的申报日期和受理日期都填成季度最后一天，历史回放判定"日期不明"，整季看不见（SHOP、AVGO、UNH、RBLX、FRC、KVUE、RDDT 等；池子成员里约 4,267 季有同季财报可以兜底）。改为：两个日期都是占位值时，用同一季的财报发布日；两个日期都有效时取较早的那个（CRM 修正申报把整季推后一年的问题）。只影响历史回放 → 96.0%。

## 已知限制

- EPS、预期、PE 不在共有因子里，S1 不验证。M4 遗留的 APH street EPS 短孤岛问题仍需一手来源核实（APH 不在原站数据里）。
- 我们口径（折算天数、按日期配对）的正确性，只在两种口径结果相同的行上被 S1 覆盖；其余行靠 M6 的单测和独立复算。
- 输入值不同的 27 条（MA 以外）没有逐条去一手来源核实。
- 由财报发布日定日期的季度，在输入包里带 `statement_date_from_earnings` 标签，在 D9 审计里列为 `public_date_from_earnings`。两个有效日期取较早时，定的是"这一季何时可见"，不是"用哪个版本的数值"；近似回放本来就对所有季度用最新数值。
- 可用日期兜底改了代码版本；M4/M6 的验收记录保留原样作为历史证据，没有重跑（2024-08-17 回放的对比除外）。
