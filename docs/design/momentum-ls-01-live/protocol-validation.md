## 保护方式的选择分支

1. 首选数量型 reduceOnly STOP_MARKET，先挂新、后撤旧。先执行 G1–G3。
2. 如果共存、更替或正常减仓冲突不符合要求，保留失败证据，回到保护方案讨论。单张 closePosition 或有界先撤后挂只能另行批准，不能运行中静默切换。
3. 如果数量型保护可靠，生产只启用这一种。不建通用多策略保护框架。
4. 如果 entryPrice 与规则不符，先解释差异和字段含义。不自动改研究规则，不加复杂成本系统。必要时回到设计决定最小修正。

## 实施计划须固定的参数

- 准备时间（默认 11:00 新加坡）、首波准入期（默认 12:00–12:05）、统一收敛期限、在途请求上限（新增/保护各 5；只计 SENDING/UNKNOWN）。
- 调仓期间订单和保护的查询频率；无正确保护的处置期限。不能用一分钟轮询替代首开保护。
- 波B 保证金预检的安全余量。
- tick/step 舍入、低于最小数量的差额处理、每动作唯一 ID 格式。
- "确认未受理"的判定：查询次数、时间跨度、无成交、仓位不变。
- 轻核对和全量核对的请求清单与权重估算；全量核对频率（默认每小时）；单次失败升级为持久暂停的连续次数。
- 存活消息时间（D2 已确认，每日必发）；守护心跳过期阈值及独立 cron 检查频率；SQLite 备份周期和重建流程；现金核对截止时点。
- 账户级故障与单币故障退出的人工门边界（D1）；"多币同时被拒"的判定阈值。
- D4 固定两波、D5 准备失败不新增、D6 保证金不足等比缩量的具体处理路径。

失败记录至少包含：环境、时间、请求用途、非敏感参数、响应错误、最终订单和仓位、核对结论。日志不得包含密钥或签名。
